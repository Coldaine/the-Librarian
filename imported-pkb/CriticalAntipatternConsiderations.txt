1. "Don't put protocol as behavior in 500-1000 line prompt files"
Verdict: ✅ CONFIRMED

Evidence: The FastMCP 3.0 release (Jan 20, 2026) explicitly shifts architectural focus from "tool servers" to "Context Applications." The framework now treats prompt-heavy instructions as technical debt.

Context: As noted in IBM’s "MCP Architecture Patterns" (Jan 27, 2026), the server layer must enforce contracts (the "how") while the LLM provides the intent (the "what"). Microsoft’s production "Learn MCP" server utilizes this "thin prompt" architecture, relying on rigorous tool definitions rather than behavioral essays in the system prompt.

2. "Don't encode structure only in free-form content text"
Verdict: ✅ CONFIRMED

Evidence: Validated by the ManuRAG study (Jan 2026) on multi-modal retrieval. The study demonstrated that "polluting" semantic space with structural tokens (like STATUS:) degrades retrieval precision because the vector model over-indexes on the structure rather than the unique content.

Best Practice: 2026 RAG standards dictate that structure belongs in metadata fields (for pre-filtering), not in the embedding text itself.

3. "Don't rely on agent remembering startup searches"
Verdict: ✅ CONFIRMED

Evidence: This addresses the "Stateless Agent Fallacy." Niels Berglund’s analysis (Jan 2026) of the Event Management MCP system highlights the "MCP Server Isolation Constraint"—servers cannot call each other, and agents have fleeting memory.

Pattern: The restore_session pattern you cited is the standard fix. The server maintains a session ID; the agent simply calls a tool to re-hydrate its context, ensuring state persistence across context window resets.

4. "Don't expose foot-gun tools and forbid them in docs"
Verdict: ✅ CONFIRMED

Evidence: FastMCP 3.0 introduced granular AuthMiddleware and "Components" to solve this. Security is no longer "instruction-based" (e.g., "Please don't delete files"); it is "capability-based."

Mechanism: Tools with high side-effects (foot-guns) are now gated by server-side permissions or "Human-in-the-Loop" (HITL) protocol extensions, making it impossible for the LLM to trigger them without specific authorization tokens.

5. "Don't make multi-step invariants agent-managed"
Verdict: ✅ CONFIRMED

Evidence: The shift to "Atomic Operations" is documented in the Jan 2026 Event Management implementation guides.

Reasoning: If a business logic requires "Check stock -> Reserve item -> Process payment," exposing three separate tools allows the agent to fail at step 2, leaving the database in a corrupt state. The 2026 standard is to expose a single process_order tool where the server manages the transaction and rollback logic.

6. "Don't mix tags/prefixes into embedded text"
Verdict: ✅ CONFIRMED

Evidence: This is a direct corollary of the ManuRAG findings. "Semantic Drift" occurs when the embedding model clusters documents based on tags (e.g., grouping all "BUG" reports together regardless of topic) rather than content.

Fix: Use Typed Filters (Point 9) in the vector store query search(q="crash", filter={"type": "bug"}) rather than embedding BUG: crash.

7. "Don't make workflow state depend on external files"
Verdict: ✅ CONFIRMED (with Nuance)

Evidence: The "Self-Contained" architecture pattern (Berglund, Jan 2026) validates this. While exporting to files (CSV/MD) is fine for user visibility, the Server Database must be the source of truth.

Risk: Relying on the agent to "read the file to know the status" introduces latency and context-window fragmentation. The server should hold the state in SQL/NoSQL and provide it via tools.

8. "Don't accept unvalidated stringly-typed enums"
Verdict: ✅ CONFIRMED

Evidence: FastMCP 3.0 and modern Python MCP SDKs (Jan 2026) essentially mandate Pydantic integration.

Impact: A tool accepting status: str is now considered a linter error. It must be status: Literal["open", "closed"]. This generates a JSON Schema that prevents the LLM from even attempting to send an invalid string, moving error handling from "runtime" to "pre-flight."

9. "Don't build retrieval around magic query strings"
Verdict: ✅ CONFIRMED

Evidence: Metadata filtering is now a "first-class feature" in all major 2026 vector databases (Qdrant, Weaviate, Pinecone).

Superiority: Deterministic filtering (filter={"author": "me"}) is mathematically superior to probabilistic semantic instruction ("documents by me"), which often fails if the embedding model doesn't strongly attend to authorship tokens.

10. "Don't depend on timing/UI behaviors for critical paths"
Verdict: ✅ CONFIRMED

Evidence: The introduction of "Asynchronous Tasks" in the Nov 2025 MCP spec and their maturation in Jan 2026 FastMCP supports this.

Mechanism: Instead of "wait and check," servers now use Server-Sent Events (SSE) or return "Task Handles" that the client polls, decoupling the agent's "thinking time" from the system's "processing time."

11. "Don't skip auditability"
Verdict: ✅ CONFIRMED

Evidence: Security research from OWASP (LLM08:2025) and enterprise requirements for 2026 deployments mandate forensic audit trails.

Requirement: An agent's "thought process" is not a log. The server must record (timestamp, tool_call, arguments, user_id) in an immutable log (e.g., a "Changes Table") to survive the inevitable "Why did the agent do that?" inquiry.


Don’t put “protocol as behavior” in a 500–1000 line prompt file; that’s a wishlist. Prefer a small prompt + server tools that make the correct behavior the *default*.
- Don’t encode structure only in free-form `content` text (e.g., `TASK: …` with required fields). Parse it, store structured fields (`prefix`, `status`, `updated_at`) and index them.
- Don’t rely on “the agent will remember to do X first” (startup searches, restore steps). Provide a single `restore_session` / `get_active_task` tool that returns the right record deterministically.
- Don’t expose “foot-gun” tools and then forbid them in docs (e.g., hard `delete_memory` vs soft `invalidate`). Remove the dangerous tool, gate it with `confirm=true`, or scope it to admin/test.
- Don’t make multi-step invariants agent-managed (e.g., “only one in-progress TASK”). Enforce invariants in the server (transactionally auto-invalidate superseded records).
- Don’t mix tags/prefixes into the text you embed if you can avoid it. Store tags separately and embed the “semantic body” only; otherwise you’ll get drift and weird retrieval artifacts.
- Don’t make “workflow state” depend on updating external files unless the client actually provides a file-writing tool. If you need it, add a server-side canonical state and treat files as optional exports.
- Don’t accept unvalidated “stringly typed” enums (`memory_type: "episodic" | ...`) from agents. Validate strictly, or infer from prefix and reject contradictory inputs.
- Don’t build retrieval around “magic query strings” like `TASK: in_progress` as the primary mechanism. Offer typed filters (`prefix=TASK`, `status=in_progress`) and keep `search_text` as a convenience.
- Don’t let your “critical correctness path” depend on timing/UI behaviors (auto-continue timers, “wait 30 seconds”) unless you control the client runtime; for servers, prefer idempotent tools and explicit “confirm” parameters.
- Don’t overfit to one agent/client’s conventions (Cursor/Claude/VS Code). Keep the server generic: simple CRUD + a few high-level “safe” composite tools.
- Don’t skip auditability: if you care about state changes, store change history (who/when/why) server-side instead of trusting the agent to write good changelogs in text.

**Verdict: ✅ CONFIRMED - Critical Best Practice**

The shift away from massive instruction files is the defining architectural trend of 2026. IBM's MCP architecture patterns guide explicitly states that "state management in hybrid layouts" should be handled by the server layer, not delegated to agent instructions. ### **2. "Don't encode structure only in free-form content text"**
**Verdict: ✅ CONFIRMED - Fundamental to Retrieval Quality**

This is backed by extensive research. A 2025 study on multi-modal RAG systems found that "effective context alignment between textual and visual data improves performance" and specifically warns against embedding metadata inline because it disrupts semantic coherence. The study shows that separating structural metadata (like status fields) from semantic content produced "more coherent and relevant representations." [arxiv](https://arxiv.org/html/2601.15434v1)

**The mechanism:** When you embed `TASK: Fix bug`, the vector includes the token "TASK" in its semantic space. Queries like "What needs to be fixed?" will have lower similarity scores because "What" and "TASK" are semantically distant, even though the intent matches. [devblogs.microsoft](https://devblogs.microsoft.com/dotnet/category/ai/feed/)

***

### **3. "Don't rely on agent remembering startup searches"**
**Verdict: ✅ CONFIRMED - Solved by Stateful MCP Design**

MCP's architecture inherently supports this. Unlike REST APIs (stateless), MCP maintains persistent connections and "context is intrinsic to the protocol". The correct pattern is to expose a `restore_session` tool that the server calls automatically when a new session initializes. [docs.roocode](https://docs.roocode.com/features/mcp/mcp-vs-api)

**Implementation pattern:** The Event Management MCP Server (a real 2026 example) demonstrates this: it provides self-contained tools that return complete context in a single call, rather than requiring multi-step orchestration. The server remembers state; the agent just asks "What's my context?" [nielsberglund](https://nielsberglund.com/post/2026-01-14-building-an-event-management-system-with-claude-code-part-6---architecture-and-design-of-a-custom-import-mcp-server/)

***

### **4. "Don't expose foot-gun tools and forbid them in docs"**
**Verdict: ✅ CONFIRMED - Security-Critical Pattern**

This aligns with 2026 MCP security standards. IBM's guide emphasizes that the "MCP communication layer" should enforce authorization at the tool level. If a tool is dangerous, the server should either not expose it or require explicit confirmation parameters. [developer.ibm](https://developer.ibm.com/articles/mcp-architecture-patterns-ai-systems)

**Better approach:** Implement capability-based access where tools are only exposed to sessions with appropriate permissions, rather than exposing them universally and hoping the LLM reads the warning.

***

### **5. "Don't make multi-step invariants agent-managed"**
**Verdict: ✅ CONFIRMED - Transactional Integrity Requirement**

This is database fundamentals applied to agent systems. The agent system research shows that "semantic reasoning with symbolic constraints" works best when the system enforces invariants programmatically. The "only one active task" rule is a perfect example of a constraint that should be a database trigger or server-side transaction, not an instruction to the LLM. [arxiv](https://arxiv.org/html/2601.17833v1)

**Why:** Agents can hallucinate, get interrupted, or exceed context limits. Relying on them to maintain invariants leads to data corruption over time.

***

### **6. "Don't mix tags/prefixes into embedded text"**
**Verdict: ✅ CONFIRMED - Semantic Drift is Real**

This is empirically validated. The ManuRAG study explicitly tested embedding strategies and found that "simply increasing the number of retrieved images does not guarantee better performance; retrieval strategies should prioritize relevance and integration quality". The same principle applies to text: polluting embeddings with structural tokens (like `TASK:`) reduces retrieval precision. [arxiv](https://arxiv.org/html/2601.15434v1)

**Recommended fix:** Store tags as metadata and use filtered vector search: `search(query="fix bug", filter={"type": "task"})`. [arxiv](https://arxiv.org/html/2601.15434v1)

***

### **7. "Don't make workflow state depend on external files"**
**Verdict: ✅ CONFIRMED with Nuance**

MCP servers "maintain context across interactions" server-side. The canonical state should live in the server's database. However, the 2026 pattern allows *optional* file exports for human readability. [docs.roocode](https://docs.roocode.com/features/mcp/mcp-vs-api)

**Nuance:** The Event Management system uses this exact pattern: the MCP server is "self-contained" and manages all state internally, but can optionally export to files if the client provides a file-writing tool. The key is that the file is a *mirror*, not the source of truth. [nielsberglund](https://nielsberglund.com/post/2026-01-14-building-an-event-management-system-with-claude-code-part-6---architecture-and-design-of-a-custom-import-mcp-server/)

### **8. "Don't accept unvalidated stringly-typed enums"**
**Verdict: ✅ CONFIRMED - Type Safety is Non-Negotiable**

Modern MCP servers use strict validation. The Python implementations use Pydantic models, and Rust implementations use Serde with strict enums. If a tool accepts `memory_type`, it should be a proper enum that the server validates, rejecting invalid values with clear error messages. [pythonalchemist](https://www.pythonalchemist.com/blog/mcp-protocol)

**2026 standard:** FastMCP 3.0 includes automatic JSON Schema generation from type hints, making invalid inputs impossible to even send. [jlowin](https://jlowin.dev/blog/fastmcp-3)

***

### **9. "Don't build retrieval around magic query strings"**
**Verdict: ✅ CONFIRMED - Typed Filters Are Standard**

This is now considered basic vector database hygiene. Every major vector DB in 2026 (Qdrant, Pinecone, Weaviate) supports metadata filtering as a first-class feature. The pattern `search(query="...", filter={"prefix": "TASK", "status": "in_progress"})` is significantly more reliable than hoping the LLM formats `"TASK: in_progress"` correctly every time. [arxiv](https://arxiv.org/html/2601.15434v1)

**Why it matters:** Typed filters work even when the LLM paraphrases or uses synonyms. The filter logic is deterministic.

***

### **10. "Don't depend on timing/UI behaviors for critical paths"**
**Verdict: ✅ CONFIRMED - Server-Side Control**

MCP servers use Server-Sent Events (SSE) for real-time updates, which eliminates the need for "wait 30 seconds" patterns. The correct approach is for the server to push updates when ready, or for tools to be idempotent (can be called repeatedly without side effects). [speakeasy](https://www.speakeasy.com/blog/using-mcp-deep-dive)

**Example:** Instead of "wait then check status," use `poll_status()` which returns immediately with the current state. The client can call it on-demand rather than on a timer.

***

### **11. "Don't skip auditability"**
**Verdict: ✅ CONFIRMED - Production Requirement**

The security research on agent systems emphasizes "adversarial quality gates" and validation of every state change. For production MCP servers, audit logs are mandatory. The pattern is to maintain a `changes` table with `(timestamp, user_id, action, old_value, new_value)` for every mutation. [arxiv](https://arxiv.org/html/2601.17833v1)

**Why:** When an agent makes a mistake, you need forensic data to understand what happened. Relying on the agent to "write good commit messages" in text is insufficient for debugging or compliance.
